INCIDENT REVIEW

장애 분석 기록

범위
현 직장에서 탐지부터 원인 규명, 조치, 재발 방지까지 직접 맡은 사례 5건
형식
현상 → 원인 분석 → 조치 → 재발 방지

1. 인증 메일 최대 16분 지연

현상인증번호 발송 API는 즉시 성공 응답. 실제 메일 수신까지 12~16분 지연
원인 분석
  • 알림 서비스 로그에서 큐 소비 시 DB 쓰기가 매번 SQL 문법 오류로 실패하는 것 확인
  • 실패한 메시지가 큐의 가시성 제한 시간(30초)마다 다시 전달되는 루프가 지연의 실체
  • 근본 원인은 애플리케이션 엔티티에 있는 컬럼 1개가 QA DB 스키마에 없던 스키마 불일치
  • 템플릿 데이터 문제 가설은 템플릿을 지운 상태에서도 정상 처리되는 것으로 배제
조치누락 컬럼 반영 후 재시도 없이 0.2초 발송 확인
재발 방지DDL의 전 환경 반영과 문서 갱신 요청. 템플릿이 DB 없이 만료 없는 캐시 값으로만 동작 중인 잠재 위험도 함께 보고

2. 매일 같은 시각 QA DB CPU 70%

현상평소 22~24%이던 QA Writer CPU가 매일 오전과 오후 같은 시각에 상승. 69~70% 상태가 11일간 지속
원인 분석
  1. 서버 cron 가설: SSM으로 서버 33대의 crontab 전수 조회, 해당 시각 쓰기 작업 없음
  2. DB 내부 스케줄러 가설: Event Scheduler 7개 확인, 관련 없음
  3. 애플리케이션 스케줄러 가설: 프레임워크 스케줄러 확인, 관련 없음
  4. 남은 경로에서 EventBridge 스케줄 2개와 Lambda 배치 발견
  5. Lambda 산출물을 디컴파일해 월 통계 약 2만 건을 지우고 다시 쓰는 로직 확인
  6. 이 대량 변경이 CDC로 QA에 그대로 복제되며 CPU를 올리는 구조로 확정
조치운영팀에 테이블 사용 여부 확인 후 해당 통계 테이블 2종을 복제 대상에서 제외
재발 방지복제 대상 선정 기준에 "주기적으로 전체를 다시 쓰는 배치 테이블 제외" 추가

3. 기동에 실패한 웹앱이 만든 DB 커넥션 누수

현상QA DB 커넥션이 주기적으로 15개에서 84개로 급증. 같은 날 애플리케이션 에러 로그 960건
원인 분석
  • 한 웹앱이 컨텍스트 초기화에 실패했지만, 실패 직전에 만들어진 커넥션 풀의 Evictor 스레드는 살아남아 30초마다 새 커넥션 생성
  • TCP 연결은 성공하지만 이미 정지된 클래스로더 때문에 다음 단계에서 예외 발생, 소켓은 열린 채 방치
  • Tomcat 기본값(clearReferencesStopThreads=false)이 경고만 남기고 스레드를 멈추지 않아 파일 삭제만으로는 해결 불가, JVM 재기동 필요
  • 운영은 다른 이유로 더 이른 단계에서 실패해 커넥션 풀이 만들어지지 않았을 뿐. 클래스 오류 하나만 고치면 운영에서도 같은 누수가 재현되는 상태
  • 해당 웹앱은 약 5년간 기동 실패 상태로 아무 서비스도 하지 않던 것 확인, 제거 결정
조치
  • rm 대신 배포 디렉터리 밖으로 mv해 즉시 복원 가능하게 처리. 자동 재배포를 막기 위해 war 먼저, 디렉터리 나중
  • 백업은 압축본과 원본 이중 보관, 파일 수와 압축 무결성 대조
  • 운영 2대는 서비스 재기동 없이 처리(배포 파일 해시와 리스닝 포트 유지 확인), QA는 해당 프로세스만 재기동
결과해당 프로세스 커넥션 82 → 1, 호스트 전체 109 → 28, 누수 로그 하루 960건 → 0건
재발 방지잔존 여부 검사 범위(배포 디렉터리, 작업 디렉터리, 자동 배포 경로, 배포 스크립트)와 롤백 순서 문서화

4. 내부 로드밸런서 전환 직후 간헐 502

현상서비스 간 파일 업로드에서 간헐 502. 3일간 148건, 직전 주 0건. 사용자 문의 3건
원인 분석
  • 직전 주 0건과 비교해 시작 시점을 내부 로드밸런서 전환 작업으로 특정
  • 에러 로그의 호출 경로로 문제 구간 확정
  • 호스트 헤더 라우팅 규칙을 HTTPS 리스너에만 추가했는데 일부 내부 호출은 HTTP로 같은 호스트를 호출. HTTP 리스너에서 기본 대상 그룹으로 잘못 전달
조치HTTP 리스너에 같은 규칙 추가. 사용자 문의 3건을 같은 원인으로 연결해 종결
재발 방지리스너 변경 시 프로토콜별 리스너 규칙 전수 대조를 전환 절차에 포함

5. 타임아웃 체인 불일치로 인한 다운로드 실패와 502

현상관리자 화면의 엑셀 다운로드 실패
원인 분석
  • 응답이 60초를 넘어 로드밸런서 유휴 타임아웃(60초)에 걸림
  • 추가로 로드밸런서는 유휴 연결을 더 오래 재사용하려는데 리버스 프록시가 65초에 먼저 닫아, 닫히는 연결에 요청이 실리며 502 발생
조치프록시 keepalive_timeout을 먼저 300초로 올리고 무중단 reload, 그다음 로드밸런서 유휴 타임아웃 300초. 순서를 바꾸면 중간 구간에 같은 502가 나는 구조
재발 방지구간별 타임아웃을 하나의 체인으로 보고 뒤 구간이 앞 구간보다 먼저 끊지 않도록 맞추는 기준 기록

공개용 문서. 회사명, 서비스와 테이블 이름, 호스트, 주소는 제외하고 일반화해 표기.
