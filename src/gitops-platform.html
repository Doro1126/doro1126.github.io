PLATFORM · CI/CD

EKS 기반 GitOps 배포 플랫폼 구축

역할
QA 신규 플랫폼 설계와 구축, 파이프라인 표준화, 운영
환경
EKS (Karpenter, Fargate), Terraform, Jenkins, Nexus, ArgoCD, Helm, External Secrets, Gateway API

배경

  • Jenkins가 산출물을 SSH로 서버에 보내고 원격 스크립트를 실행하는 Push 방식 배포
  • 서비스마다 파이프라인 스크립트가 달라 빌드와 배포 기준이 한 곳에 없는 상태
  • 어떤 버전이 어디에 배포됐는지 Git으로 추적 불가
  • 설정 파일에 DB 비밀번호와 AWS 액세스 키가 기본값 형태로 커밋된 서비스 존재

구조

개발자 push→Jenkins CI→Nexus
이미지, 차트, 라이브러리→GitOps 저장소
이미지 태그 커밋→ArgoCD→EKS
  • Jenkins는 빌드, 이미지 push, GitOps 저장소 커밋까지만 담당. 클러스터 반영은 ArgoCD 전담
  • Nexus는 아티팩트 저장소, Git은 "무엇을 배포할지"의 기록. 롤백은 GitOps 커밋 revert
  • 저장소는 서비스 소스, CI(Dockerfile과 Shared Library), 공용 Helm 차트, GitOps, Terraform으로 분리
  • 공용 차트 1개에 서비스별 values로 차이 표현. 서비스마다 차트를 만들지 않는 구조

App-of-Apps

  • root Application이 환경별 apps 디렉터리를 재귀 등록. 신규 서비스 배포는 Application.yaml과 values.yaml 2개 파일 추가로 끝
  • ApplicationSet 대신 App-of-Apps 선택. 서비스마다 네임스페이스, 차트 버전, values 구조가 달라 개별 Application이 더 명확하다는 판단
  • root를 앱용(prune 사용)과 플랫폼용(prune 미사용)으로 분리. AppProject도 나눠 개발자와 CI 계정은 앱 범위만 접근

Jenkins Shared Library

  • 원자 함수 7개: checkout, 이미지 빌드, push, 이미지 정리, GitOps values 갱신, ArgoCD sync, 알림. 함수끼리 서로 호출하지 않는 구조
  • 조합 템플릿 4개: QA 자동 배포, 운영 빌드, 운영 배포(수동 승인), 수동 검증용
  • 운영은 Build와 Deploy Job 분리. Deploy가 실행 시점에 Nexus의 최신 태그를 직접 조회하고 승인 게이트를 거치는 구조

Terraform과 ArgoCD 관리 경계 정립

기준: 쿠버네티스 API 밖이면 Terraform, 안이면 ArgoCD. 예외는 부트스트랩뿐.

리소스이전이후
VPC, EKS, IAM, DB, 보안 그룹TerraformTerraform
ArgoCD, KarpenterTerraformTerraform (부트스트랩 예외)
Gateway API CRD, Traefik, ESO, ALB Controller 차트TerraformArgoCD (sync wave로 순서 제어)
ALB Ingress, 내부 NLB Service수동 kubectl applyArgoCD
ArgoCD 계정과 RBACTerraform patchArgoCD selfHeal (부분 소유)
  • 이관 순서: Application 추가(자동 sync 없이) → diff로 동일 확인 → terraform state rm → 수동 sync로 인수 → 기능 검증. destroy 미사용
  • 결과: terraform plan No changes, Application 16개 Synced/Healthy, 어노테이션 248KB → 0, 서비스 중단 없음

시크릿과 설정값 분리 표준 수립

값관리 위치
시크릿Secrets Manager + External Secrets (서비스별 시크릿 1개)
비시크릿 설정값GitOps values의 ConfigMap
AWS 자격 증명사용하지 않음. EKS Pod Identity
프론트엔드 빌드 변수소스 저장소의 프로필별 예시 파일 (빌드 시 이미지에 포함)
  • 설정 파일의 평문 기본값 제거 6개 서비스. 정적 액세스 키 문자열 0건 확인
  • IRSA 대신 Pod Identity 선택. 공용 라이브러리에 STS 모듈이 없어 IRSA 토큰 단계를 에러 없이 건너뛰고 노드 역할로 넘어가는 동작 확인. Pod Identity는 라이브러리 수정 없이 적용 가능
  • IAM은 서비스 전체 권한 정책 대신 서비스별 역할과 실제 호출 액션만 허용
