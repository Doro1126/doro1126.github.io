OBSERVABILITY

레거시 관제 대체와
Prometheus · Grafana · Loki 모니터링 구축

역할
대안 검증, 설계, 운영 서버 30대 적용, 알림 체계 설계
환경
EC2 기반 운영 서버, Prometheus, Grafana, Loki(S3), Promtail, Node Exporter, Blackbox Exporter, AWS SSM, Terraform

배경

  • 기존 관제는 Logstash, JDBC, 자체 웹앱으로 만든 사내 시스템. 서버 1대에서 단독 동작, 디스크 사용률 92%
  • 서비스가 죽었는지는 "수집 실패" 알람으로만 간접 확인. 에러 로그는 앱이 직접 HTTP로 보내는 방식
  • 대체 후보로 상용 APM을 시험 적용하던 중 에이전트 기능 활성화 직후 운영 6대와 QA 2대에서 OOM Kill 발생
  • 운영 서버 다수가 메모리 1GB급 소형 인스턴스이고 대부분 Swap 없음. 다음 날 상용 APM 에이전트 전면 철수 결정

  • QA에서 먼저 구축하고 같은 버전과 설정 형식으로 운영에 적용

  • 모니터링 서버는 공인 IP 없는 사설 서브넷에 배치. Docker Compose로 4개 컨테이너 구성, 컨테이너별 CPU와 메모리 상한 지정
  • Loki 저장소는 로컬 디스크 대신 S3. 접근은 액세스 키 없이 인스턴스 프로파일로 처리
  • 수집 포트는 모니터링 서버의 보안 그룹만 출처로 허용 (전체 대역 개방 없음)

서비스 DOWN 감지

  • "수집이 끊기면 알림" 대신 운영 서버 30대의 앱 포트 40여 개를 Blackbox Exporter로 직접 TCP 확인. probe_success == 0이면 DOWN
  • 알림에 서버와 서비스 라벨을 함께 붙여 어느 서버의 어떤 앱인지 바로 식별
  • 대상 목록은 3가지로 교차 확인: ss -tlnp의 리스닝 포트와 PID, 프로세스 작업 디렉터리, 프로세스 관리 도구 상태와 인프라 문서

알림 설계

기존 기준 역추적

  • 레거시 관제의 이벤트 13종, 임계치, 알림 채널, 발송 시간대(평일 주간만)를 먼저 조사해 Grafana 규칙과 1:1 매핑표 작성 후 전환
  • 임계치 단계는 3단계 → 2단계로 축소

알림 피로 관리

  • Contact Point를 복구 알림이 필요한 것과 필요 없는 것으로 분리. type 라벨 4종으로 라우팅
  • 에러 로그 알림은 10분 반복 억제, 복구 알림 없음
  • 이미 에러가 상시 발생하는 서버 2대는 원인 정리 전까지 에러 로그 알림에서 제외
  • 알림 메시지에 서버 이름, 현재 값, 해당 서버가 선택된 대시보드 링크 포함
  • WARN 알림은 LogQL 템플릿으로 표준화. 서비스 이름만 바꿔 추가하는 방식
  • 새 알림은 테스트 채널에서 검증 후 운영 채널로 이동. SSM으로 테스트 로그 주입 → 수집 → 알림 발생 → 수신까지 끝에서 끝으로 확인

배포와 자동화

  • AWS SSM Run Command로 운영 30대에 일괄 설치. 설치, 서비스 등록, 설정, 활성화, 확인 순서 고정
  • Promtail 시작 전에 positions.yaml 오프셋을 미리 기록해 과거 로그 전체가 다시 수집되는 문제 예방
  • 운영 서버 로그 경로를 전수 조사해 공통 규칙 도출. 미사용 서비스와 HA 유틸리티 로그는 수집 제외
  • 서버별 로그 대시보드는 Terraform으로 생성. Loki API에서 현재 로그를 보내는 서버 목록을 받아 for_each로 만들고, UID 고정과 overwrite = false로 기존 대시보드 보호

운영 중 문제와 해결

문제해결
Grafana 신버전에서 Terraform 대시보드 배포 실패 (루트 id 거부)프로바이더 상향과 클래식 JSON 형식 템플릿으로 전환
로그 파일 약 3,000개가 쌓인 서버에서 Promtail 메모리 206MB해당 서버는 메트릭만 수집하도록 예외 처리
파일 로그 없이 journald만 쓰고 디스크가 작은 서버 2대로그 수집 보류, 메트릭만 수집
설치 전 디스크 92~97% 서버 존재설치 전 정리 대상으로 분류해 적용 범위 결정
CLI 조회 결과가 일부만 나와 서버 수 오인페이지네이션과 필터 수정 후 운영 VPC 전체 43대 확인
