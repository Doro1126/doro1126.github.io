DATABASE

Aurora MySQL 5.7 → 8.0 업그레이드와
QA 실시간 동기화 전환

역할
업그레이드 주도, QA 동기화 구조 설계와 구축 (성능 개선 일부는 개발팀과 협업)
기간
약 4개월 (테스트 환경 검증 약 3개월 포함)
환경
Aurora MySQL, QA와 운영 2개 환경, DMS Serverless

배경

  • 운영 DB가 표준 지원이 끝난 5.7 버전이라 연장 지원(Extended Support) 요금 발생. 월 DB 비용의 약 53%가 버전 유지 비용
  • QA 데이터는 매일 운영 Writer에서 전체 덤프 후 삭제·재적재하는 방식. 운영 DB 부하와 하루 단위 데이터 지연이 함께 발생
  • DB CPU 알람이 매일 울리는 상태라 업그레이드 전에 성능 문제부터 정리 필요

사전 검증

스키마 정적 분석

  • MySQL Shell util.checkForServerUpgrade()로 스키마 점검. 5.7 → 8.0.42 기준 Fatal 0건, Warning 194건
  • 항목을 "8.0에서 깨지는가 / 8.4에서 깨지는가" 기준으로 분류. 다음 메이저 업그레이드까지 고려한 우선순위
  • 사용 중인 테이블 전수 조사 후 전체의 16% 삭제, 72% 수정
  • 버전 충돌 요소 정리: 8.0 예약어(ADMIN)와 겹치는 컬럼명, utf8mb3 → utf8mb4, Zero Date 기본값, 8.0에서 동작이 바뀐 비밀번호 함수 쿼리

파라미터 그룹

  • QA는 클러스터 파라미터 그룹만 커스텀, 운영은 인스턴스 파라미터 그룹에도 커스텀 값 존재. 놓치면 max_connections 등이 기본값으로 돌아가는 구조라 환경별로 따로 대조
  • 8.0의 기본 collation 변경에 대비해 character_set_server, collation_server 명시. 신규 테이블과 기존 컬럼 간 collation 충돌 예방

운영 업그레이드

서비스 이용이 가장 적은 새벽 점검 창에서 진행. 계획한 종료 시각 전에 서비스 장애 없이 완료.

사전 공지→점검 화면→스냅샷→충돌 제거→1차 확인→8.0.42→2차 확인→재개
  • 스크립트 실행 전과 버전 업그레이드 전에 스냅샷을 각각 확보
  • 진행 중 터미널 로그, 커넥션 풀 그래프, 콘솔의 엔진 버전, 실제 접속 결과를 함께 확인
  • 점검 화면은 로드밸런서 고정 응답으로 준비하고 QA에서 리허설. 앱과 웹이 공통으로 다르게 보내는 요청 헤더 1개로 분기해 앱에는 JSON, 웹에는 HTML 503 반환
  • 고정 응답 본문 1024자 제한은 점검 이미지를 외부 저장소에 두고 참조하는 방식으로 해결

프리체크 실패 2회

환경원인조치
QA미사용 스키마의 컬럼 코멘트에 이모지 등 4바이트 문자 포함미사용 스키마 삭제 후 재시도
운영utf8mb3 코멘트 검사 12건 실패. information_schema에서는 코멘트가 빈 값인데 프리체크만 에러로 판정. 내부 딕셔너리에 남은 손상 바이트 문제(MySQL Bug #110177)해당 테이블·컬럼 코멘트를 빈 값으로 재작성 후 재시도
  • 콘솔에 상세 사유가 나오지 않아 Writer 인스턴스의 프리체크 로그를 CLI로 내려받아 에러 항목만 추출하는 절차 정리
  • 프리체크 실패 시 클러스터가 5.7 상태로 남고 다운타임이 없다는 점 확인
  • 완료 후 롤백은 스냅샷 복원뿐이고 엔드포인트가 바뀐다는 점을 사전에 공유. 5.7 → 8.0과 8.0 → 8.4는 묶지 않는 원칙

업그레이드 후 발견한 장애 2건

증상원인조치
알림 API는 200인데 실제 발송 없음발송 데몬의 2016년경 JDBC 드라이버가 접속 시 8.0에서 제거된 query_cache_size 변수를 조회하다 예외 발생8.0 호환 드라이버로 교체
자동 배정 API 500 반복8.0의 ICU 정규식 엔진에 새로 생긴 실행 시간 제한(regexp_time_limit, 기본 32ms) 초과재부팅 없이 파라미터 조정. 쿼리 개선을 후속 과제로 등록

QA 동기화: 덤프 배치 → DMS CDC

이전

  • 운영 Writer에서 전체 덤프
  • 하루 1회, 전체 삭제 후 재적재
  • 셸 스크립트와 cron으로 관리

이후

  • binlog 기반 변경분만 복제
  • 실시간, 268개 테이블
  • DMS Serverless 관리형
  • 운영과 QA VPC 대역이 같아 Peering 불가. QA DB를 다른 대역 VPC로 옮긴 뒤 Peering과 DNS 해석 설정. 인터넷 경유 없이 복제
  • 이관 과정에서 전체 개방돼 있던 QA DB 보안 그룹을 출처별 허용 목록으로 축소
  • 트러블슈팅 6건 문서화: FK 제약, 중복 키, Lock 대기, DMS 세션 UTC로 인한 9시간 차이, 대형 테이블 제외 판단 등
  • DMS가 테이블·컬럼 코멘트를 복제하지 않는 제약 확인과 재동기화 절차 정리
  • 업그레이드 다운타임 동안 CDC 지연이 최대 21분까지 늘었다가 자동 회복, 데이터 손실 없음

8.4 LTS 준비 (분석까지 완료)

8.4 변경대응 방향
기본 인증 플러그인 파라미터 제거신규 인증 정책 파라미터로 유지 또는 계정별 전환
TLS 1.2 CBC 계열 cipher 제거GCM/CCM 계열로 재설정
thread_handling=thread-pools 무효커넥션 규모 실측 후 기본 방식으로 변경
require_secure_transport 기본값 ON파라미터로 유지 또는 클라이언트 TLS 전환
  • 마지막 항목은 레거시 서비스 코드를 직접 확인해 비TLS 설정이 하드코딩된 서비스 6종과 DMS 엔드포인트를 영향 대상으로 확정
  • 이 Aurora 환경에서는 DB 쪽에서 세션별 TLS 여부를 확인할 방법이 없어 클라이언트 설정 확인이 유일한 방법
