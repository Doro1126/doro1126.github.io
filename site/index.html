앱 전환 직후 파일 업로드가 WAF에 차단된 건

해결
영향 범위
앱 파일 업로드 실패
발생 시점
앱 프레임워크 전환 직후
담당
원인 분석 · 규칙 수정

현상

앱을 Flutter로 전환한 직후, 일부 사용자의 파일 업로드가 403으로 실패했습니다.

WAF 로그에서 SQL Injection 규칙이 업로드 요청을 차단한 기록을 확인했습니다.

원인 분석

새 HTTP 라이브러리는 업로드 구분자가 "----"로 시작하는데, 이것이 SQL 주석 패턴으로 오인되고 있었습니다.

30일치 로그를 대조해 기존 라이브러리 요청은 한 번도 걸리지 않았고, 새 라이브러리 요청은 등장 즉시 차단됐다는 것을 확인했습니다.

조치

해당 규칙의 업로드 본문 검사만 관찰 모드로 바꾸고, 업로드 경로에만 예외를 두는 Custom Rule을 추가했습니다.

다른 요청은 기존처럼 그대로 검사되도록 범위를 좁혔습니다.

재발 방지

예외는 IP가 아니라 경로와 라벨 기준으로 관리하도록 바꿨습니다.

새 규칙은 하루 동안 정상 트래픽 매칭 0건을 확인한 뒤에만 차단으로 전환하는 기준을 정했습니다.

허용된 IP가 차단되면 상세 내역이 Slack으로 바로 오도록 알림을 만들었습니다.

결과
  • 업로드 정상화
  • 규칙 전환 기준 수립

인증번호 메일이 최대 16분 늦게 도착한 건

해결
영향 범위
이메일 인증 지연
발생 시점
신규 알림 서비스 QA 검증 중
담당
원인 분석 · 검증

현상

인증번호 요청 API는 바로 성공으로 응답하는데, 실제 메일은 최대 12~16분 뒤에 도착했습니다.

원인 분석

알림 서비스 로그에서 DB 저장이 매번 실패하는 것을 확인했습니다.

코드에는 있는 컬럼이 QA DB 스키마에는 반영되지 않아 저장 쿼리가 실패하고 있었습니다.

저장에 실패한 메시지가 큐에서 30초마다 다시 전달되며 재시도를 반복한 것이 지연의 원인이었습니다.

조치

누락된 컬럼을 추가한 뒤 재시도 없이 0.2초 만에 발송되는 것을 확인했습니다.

다른 데이터를 지운 상태에서도 바로 처리되는지 확인해, 이 컬럼이 유일한 원인임을 확정했습니다.

재발 방지

같은 변경을 모든 환경에 정식 반영하고 스키마 문서도 갱신하도록 요청했습니다.

조사 중 발견한 별건도 함께 보고했습니다.

메일 템플릿이 DB 없이 만료 시간 없는 캐시에만 남아 있어, 캐시가 재시작되면 바로 발송이 실패할 수 있는 상태였습니다.

결과
  • 발송 지연 16분 → 0.2초
  • 숨은 장애 위험 사전 보고
장애 보고서

매일 같은 시각 QA DB CPU가 70%까지 오른 건

해결
영향 범위
QA DB 성능 저하
발생 기간
11일간 하루 두 번 반복
담당
원인 추적 · 조치

현상

매일 10시와 18시에 CPU가 평소 20%대에서 70%까지 오르는 패턴을 확인했습니다.

시간이 정확히 반복된다는 점에서 예약 작업을 먼저 의심했습니다.

원인 분석

VPC Flow Logs로 해당 시각 DB에 붙는 접속 출처를 좁히고, 서버 33대의 크론, DB 이벤트 스케줄러, 애플리케이션 스케줄러를 차례로 확인하며 후보를 지웠습니다.

마지막으로 남은 Lambda 배치를 디컴파일해, 월별 통계 약 2만 건을 지우고 다시 쓰는 로직을 찾았습니다.

이 대량 변경이 실시간 복제로 그대로 넘어오며 부하를 만들고 있었습니다.

조치

운영팀과 테이블 사용 여부를 확인한 뒤 해당 통계 테이블을 복제 대상에서 제외했습니다.

재발 방지

복제 대상 테이블을 추가하거나 뺄 때 확인할 기준을 정리했습니다.

원인 분석 과정은 같은 유형의 부하를 빠르게 찾을 수 있도록 문서로 남겼습니다.

결과
  • 반복 부하 원인 제거
  • 복제 대상 관리 기준 수립
